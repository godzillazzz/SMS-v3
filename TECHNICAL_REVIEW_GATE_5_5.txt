CURRENT LIMITER REVIEW

Previous store: one in-process JavaScript Map.
Previous algorithm: fixed window.
Previous scope/key: request IP only through Express req.ip.
Previous default window: 15 minutes.
Previous default maximum: 10 login requests per window.
Previous denial response: generic HTTP 429.
Previous risk: each Vercel function instance had an independent counter, so
limits could be bypassed across cold starts and parallel instances. Proxy IP
handling was also not explicit.

CHOSEN ARCHITECTURE

PASS — A rate-limit store abstraction now provides:
- an in-memory implementation for tests and local development;
- a PostgreSQL implementation for shared serverless staging state.

PASS — Login uses separate fixed-window scopes for normalized client IP and
normalized account identifier.

PASS — In Vercel context, client IP is read from the platform-provided
x-vercel-forwarded-for header. Local execution ignores forwarded headers and
uses the direct Express request IP.

PASS — Each identity is transformed with HMAC-SHA256 using a dedicated backend
secret before storage. Rate-limit rows contain no raw IP address or raw account
identifier.

PASS — The PostgreSQL counter uses a single INSERT ... ON CONFLICT ... DO UPDATE
statement and increments the existing count atomically.

PASS — PostgreSQL unavailability fails closed with a generic HTTP 503. There is
no silent fallback to an in-process store and no internal failure detail in the
public response or limiter log event.

PASS — Above-limit login returns a generic HTTP 429 with Retry-After,
RateLimit-Limit, RateLimit-Remaining, and RateLimit-Reset headers. Existing
browser/mobile authentication behavior was not otherwise changed.

PASS — Password-reset endpoints do not exist. Refresh throttling was not added
because it requires a separate session-aware policy and could disrupt browser
startup session restoration.

LIMITER POLICY

Algorithm: fixed window.
Default window: 900000 milliseconds (15 minutes).
Default maximum: 10 requests per login scope per window.
Scopes: login-ip and login-account.
Denial threshold: the first 10 requests are allowed; request 11 is denied.
Reset behavior: a new bucket begins at the next fixed-window boundary.
Failure behavior: generic HTTP 503 when the selected PostgreSQL store cannot
evaluate a request.
