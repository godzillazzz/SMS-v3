SMS v3 Gate 5.6B2A Technical Review
Milestone: Shared PostgreSQL Alert Deduplication Foundation
Review date: 2026-07-22

CURRENT COOLDOWN LIMITATION
PASS - The prior implementation used process-local memory. Separate serverless
instances could therefore maintain independent counters and cooldowns and could
independently consider the same alert eligible for delivery.

SHARED DEDUPLICATION ARCHITECTURE
PASS - A vendor-independent alert-deduplication store abstraction now supports
an in-memory local/test implementation and a PostgreSQL shared-state
implementation. Memory remains the default. The PostgreSQL implementation uses
the existing Prisma data-access boundary. External alert delivery remains
disabled by default.

PRISMA MODEL AND MIGRATION RESULT
PASS - A dedicated alert-deduplication model and migration were added. The
migration creates only the alert-deduplication table, its primary key, one
delivery-state check constraint, one coordination unique index, and one expiry
index. It contains no seed data and does not alter, drop, truncate, update, or
delete any existing application table.

PRIVACY-SAFE KEY RESULT
PASS - Deduplication keys use keyed HMAC-SHA256. Inputs are limited to an
approved event category, sanitized route template or a global label, safe
deployment-environment label, and aggregation-window timestamp. Tests confirm
that identity, request ID, raw error data, and route query strings do not affect
the key. Raw key input and resulting HMAC values are not logged or returned.

ATOMIC COUNTER AND AGGREGATION RESULT
PASS - The PostgreSQL store uses one atomic insert-or-update statement with a
unique coordination key. The in-memory concurrency regression test completed
50 parallel reservations with an exact final occurrence count of 50 and no lost
updates. Threshold aggregation, duplicate suppression, cooldown expiry, and
key-specific reset tests passed.

SHARED-INSTANCE TEST RESULT
PASS - Two independently constructed policy-engine instances using the same
store observed the same occurrence counter and cooldown decision.

DELIVERY-STATE RESULT
PASS - Stored delivery states are restricted to pending, suppressed, delivered,
and failed. No destination, message body, provider response, credential, token,
cookie, or raw identity is stored. The no-op delivery path continues to report
that no external delivery occurred.

FAILURE-POLICY RESULT
PASS - Shared-store failure returns a safe unavailable category, reports neither
deduplication nor delivery success, and does not invoke delivery. Failure while
updating delivery state also cannot produce a false delivered result. Operational
failure logging uses allowlisted fields only.

CLEANUP AND RETENTION RESULT
PASS - An explicit cleanup operation deletes only expired records through the
dedicated alert-deduplication Prisma model. Suggested staging retention is seven
days and remains subject to operational approval. Cleanup was not scheduled or
added to build, startup, serverless initialization, or ordinary request handling.
